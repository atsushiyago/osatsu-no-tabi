# ホームのFirestore読み取り最適化

## 通知の契約

- `firstRegisteredByMe: true` の追跡文書を全件取得する。従来のホームと同じ対象で、追跡枚数による打ち切りはしない。
- 公開紙幣はIDの `in` クエリ（30件ずつ）で全対象のサマリーを読む。バッチ化は通信数の削減であり、文書読み取り数を1件と数えない。
- 公開の `sightingsCount` と本人の `lastSeenSightingsCount` で、既存と同じ未読件数・並び順を計算する。`notifyOnRediscovery` の値や既存baselineは変更しない。
- ホームに経路を表示する通知先頭の1枚だけ発見履歴を読む。他の未読紙幣も通知枚数に含める。先頭の経路は以前と同じ「公開履歴の最後の2地点」。
- baseline未設定の旧データには、以前と同じ初回の静かなbaseline設定を行う。これは新しい移行や一括更新ではない。
- 取得失敗を「未読なし」としてキャッシュせず、通知確認失敗を表示して更新操作を案内する。
- 追跡一覧・紙幣詳細・Google統合のデータ形式は変更しない。Firestore Rules・インデックス・App Checkの変更は不要。

## キャッシュと鮮度

- 公開のホーム統計・最近の旅と、UIDごとの通知に30秒のメモリ内キャッシュを使用する。ブラウザの永続ストレージには保存しない。
- 有効期間は取得開始から計測する。同じ取得が進行中なら重複開始しない。失敗は保持しない。
- UID変更、Google連携・統合完了、本人の登録成功、詳細での既読更新成功で通知キャッシュを無効化する。登録成功時は公開ホームキャッシュも無効化する。
- 無効化前の通信が後から完了しても古い値をキャッシュに戻さない。画面の非同期結果も離脱後には反映しない。
- ホームへ戻る・表示中のタブへ復帰する際に、有効期限が切れていれば再取得する。「最新情報に更新」は両キャッシュを無効化して再取得する。
- 他端末からの登録・既読操作はキャッシュへ即時通知されない。取得から30秒以内の再訪では古い表示が残り得る。
- 表示し続けているホームを定期ポーリングはしない。放置中の表示は30秒で自動更新されるわけではなく、更新ボタン、再訪、タブ復帰で確認する。従来のホームにもリアルタイム更新はない。

## 読み取り予算の比較

前提：全N枚が本人の初回登録、baseline設定済み・未読なし、各紙幣1発見、最近の旅8枚も各1発見。統計は約3読み取り相当、最近の旅は8＋8。

| N | 修正前のホーム | 修正後の初回・期限切れ | 30秒以内の再訪（無効化なし） |
| ---: | ---: | ---: | ---: |
| 0 | 20 | 20 | 0 |
| 20 | 79 | 59 | 0 |
| 100 | 319 | 219 | 0 |
| 350 | 1,069 | 719 | 0 |

一般形では、修正後は `統計＋最近の旅＋max(1,本人初回登録の追跡数)＋その公開紙幣数＋通知先頭1枚の履歴数`。未読があれば先頭の履歴数が加わり、既存baselineの更新が必要なら従来どおりその書き込みとRules依存読み取りが発生する。修正前は初回登録以外の追跡文書もホームで読むが、修正後は読まない。

これはオンラインでのコード上の予算であり、実請求・HTTP回数の実測ではない。空クエリの最低読み取り、集計のインデックス読み取り、Rulesの依存読み取り、SDK再試行等を区別する。

## 一覧復元

追跡一覧の2区分とも、マウント時の復元対象をrefに保持する。復元完了で親が対象propsをクリアしても取得Effectを再実行せず、復元した追加ページも維持する。UID変更は親のkeyで再マウントし、再試行ボタンは従来どおり再取得する。
