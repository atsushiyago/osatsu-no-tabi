# ホームのFirestore読み取り最適化

## 通知の契約（全国の再発見済みサマリーから照合）

- 本人の `firstRegisteredByMe: true` の件数Nを集計する。0件なら終了する。
- `publicBills where sightingsCount > 1` の件数を、`limit(N + 1)` 付きの集計で調べる。全国件数が大きくても、計画決定のためだけに全インデックスを走査しない。
- 全国の再発見済み紙幣数RがN未満なら、その公開サマリーと、対応する本人の追跡文書だけを読む。本人の初回登録ではない紙幣・他人の紙幣は通知しない。`notifyOnRediscovery` は従来どおりホーム抽出条件に使わず、その値も変更しない。
- RがN以上なら、従来どおり本人の初回登録文書を全件取得し、公開サマリーを30件ずつ `in` クエリで取得する。打ち切りはしない。
- 集計は取得計画の予測にだけ使う。集計後に全国候補が増えて公開取得上限N+1件に達した場合も、本人の全件取得に切り替える。既に取得した公開文書は再利用する。上限までの取得を全件取得と誤認しない。
- 公開の `sightingsCount` と本人の既読baselineで、既存と同じ未読件数・並び順を計算する。複数回の再発見はすべて差分件数に含める。
- ホームに経路を表示する通知先頭の1枚だけ発見履歴を読む。他の未読紙幣も通知枚数に含める。先頭の経路は以前と同じ「公開履歴の最後の2地点」。
- baseline未設定の旧データは、本人の初回登録分である **1** だけを既読として補完する。過去の既読位置は復元不能なので、現在の発見回数まで静かに既読にして通知を消す方法は使わない。過去に読んだ再発見が再通知される可能性がある。保存済みbaselineは保持する。
- 補完は既存追跡文書の同じフィールドへの条件付きトランザクション。再読み取りで他端末の既読更新を確認し、既に値があれば上書きしない。旧文書が発見1回のまま全国候補に含まれなくても、将来2回になった時にbaseline=1で通知できる。永続的な移行マーカーや全追跡文書の初期走査は不要。
- 所有紙幣の一覧も同じ補完処理を使い、一覧を開くことで未読を静かに消さない。他者が初回登録した追跡セクションは従来の読み取り専用の扱いを維持する。
- 詳細からの既読更新もトランザクションにし、新クライアント同士で古い表示が既読位置を巻き戻すことを防ぐ。表示した発見回数より後の再発見は既読にしない。
- クエリ・個別取得はサーバー取得に限定する。集計・途中バッチ・履歴・旧baseline補完の失敗を「未読なし」として返したりキャッシュしたりしない。通知確認失敗を表示し、ホームを開き直しての再確認を案内する。オフラインでキャッシュの一部分だけを成功扱いしない。
- 追跡一覧・紙幣詳細・Google統合のデータ形式は変更しない。Firestore Rules・インデックス・App Checkの変更は不要。

## キャッシュと鮮度

- 公開のホーム統計・最近の旅と、UIDごとの通知に30秒のメモリ内キャッシュを使用する。ブラウザの永続ストレージには保存しない。
- 有効期間は取得開始から計測する。同じ取得が進行中なら重複開始しない。失敗は保持しない。
- UID変更、Google連携・統合完了、本人の登録成功、詳細での既読更新成功で通知キャッシュを無効化する。登録成功時は公開ホームキャッシュも無効化する。
- 無効化前の通信が後から完了しても古い値をキャッシュに戻さない。画面の非同期結果も離脱後には反映しない。
- ホームへ戻る・表示中のタブへ復帰する際に、有効期限が切れていれば再取得する。手動更新ボタンは表示しない。
- 他端末からの登録・既読操作はキャッシュへ即時通知されない。取得から30秒以内の再訪では古い表示が残り得る。
- 表示し続けているホームを定期ポーリングはしない。放置中の表示は30秒で自動更新されるわけではなく、再訪、タブ復帰で確認する。従来のホームにもリアルタイム更新はない。

## 読み取り予算の比較

前提：Nは本人の初回登録数、Rは全国の再発見済み紙幣数。baseline設定済み。通知以外の統計・最近の旅をB、先頭通知の履歴をHとする。集計の概算読み取り相当を `C(x) = max(1, ceil(x / 1000))` とする。インデックスの実走査や再試行によって変わるため実測請求値ではない。

- 従来（a49aa4e）：`B + max(1, N) + N + H`（全公開文書が存在する前提）。
- 新方式・R < N：`B + C(N) + C(R) + max(1, R) + R + H`。
- 新方式・R >= N：`B + C(N) + C(min(R, N+1)) + 2N + H`。
- N=0：`B + 1`。30秒キャッシュ有効中の再訪は従来どおり0。

R=2が変わらない場合の通知部分のみの比較（BとHは別途加算）：

| N | a49aa4e | 新方式（集計込み） |
| ---: | ---: | ---: |
| 0 | 1 | 1 |
| 10 | 20 | 約6 |
| 20 | 40 | 約6 |
| 100 | 200 | 約6 |
| 350 | 700 | 約6 |
| 1,000 | 2,000 | 約6 |
| 10,000 | 20,000 | 約15 |

従来のB=19という小規模データの例なら、350枚のホームは約719から約25＋Hに減る。N=10,000のときまでB=19とは仮定しない。全国件数が増え、N=20/R>=20なら通知は約42（従来40）で、集計2回相当の上乗せに抑える。集計後の急増による切り替えでは、一時的に最大N+1件の公開取得が追加されるが、途中結果は返さない。

新たな通知用書き込みは0。旧baseline補完が必要な文書は、原則一度のトランザクション読み取り＋1更新とRules依存読み取りが発生する。競合時は再試行分が増える。補完失敗は通知確認失敗として扱う。

これはオンラインでのコード上の予算であり、実請求・HTTP回数の実測ではない。空クエリの最低読み取り、集計のインデックス読み取り、Rulesの依存読み取り、SDK再試行等を区別する。

## 制約と戻し方

- 全国方式は未読だけをサーバーで抽出する方式ではない。全国の再発見候補を本人の情報と照合する。読み取りコストが有利でない場合は自動的に本人の全件方式を選ぶ。
- 常時リアルタイム・複数クエリ間の同一時点のスナップショットは保証しない。確認途中に発生した再発見は次回のサーバー確認で検出する。30秒キャッシュと放置中の更新条件は下記と同じ。
- 既存Rulesは既読値の減少を禁止していない。今回の新クライアント同士はトランザクションで保護するが、旧版を開いたままの端末の古い更新までRulesで拒否する変更は行わない。
- 明示的に従来の取得方式へ戻す場合は、`loadHomeTrackedBills(db, uid, { strategy: 'owned' })` を使う。集計と全国候補取得を省略するが、安全な旧baseline補完は維持する。既読情報や公開紙幣、履歴を巻き戻す操作は不要。切り替え時は既存の `invalidateHomeNotifications()` で30秒キャッシュを消す。
- 第三者の追跡情報を読む権限は追加しない。Google統合の元・宛先データ形式、重複時の宛先優先、匿名UID維持は従来どおり。既存Rulesがエクスポート元のbaselineを必須とするため、統合previewで未設定の本人初回登録IDだけを記憶し、了承後・ロック前に同じ保守的な補完を行う。キャンセル時は補完しない。発見1回の旧文書をホームで読まないことによる統合失敗を避ける。既存baselineのある通常の統合に追加読み取り・更新はない。
- 旧版ですでにbaseline不足により失敗し、有効な統合ロックが残っている場合、そのロックを迂回して補完しない。期限切れ後の既存の再確認・新規チケット経路で補完する。過去の既読位置自体が未保存の場合は復元できず、通知の重複より見逃しの回避を優先する。

## 一覧復元

追跡一覧の2区分とも、マウント時の復元対象をrefに保持する。復元完了で親が対象propsをクリアしても取得Effectを再実行せず、復元した追加ページも維持する。UID変更は親のkeyで再マウントし、再試行ボタンは従来どおり再取得する。
